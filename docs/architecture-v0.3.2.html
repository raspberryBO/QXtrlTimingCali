读图要点

  • 唯一跨边界接口是 contracts 里的五种消息：审查端与执行端之间只有 ExperimentRequest（含申请时的 config_hash）→ ExperimentResult，以及批准后的 WritePlan 下发； 换 QXtrl 只换适配器，不改裁决逻辑。
  • 分组测量，统一求解：读取线必须先对齐、再加 headroom 整体右移，测完就写回； 单比特与耦合器这两组之间一个字节都不写，所有 skew 描述同一基线；步 5 把这两组观测合并做 一次加权最小二乘（1/σ²）摊到整张图，再用一张 WritePlan 走完四道守卫； 步 6 每条读取线以其首个腔的 qubit.xy 为锚收尾：加了 headroom 就把授予的 余量收回、往左拉回对齐（收回量不超出授予余额），没加则读取线本来就在左边、只向右拉。 这是"误差不再沿链路累加"的根因——同一组输入，旧流程累计位移 33067.5 ns，批量流程只需 2860.1 ns。
  • 回写单位就是线，不再有同步块：块簿记是"逐步合并"模型的产物， 批量模式里它被末尾的一次全局求解取代；pending 文件始终只有 {line, delay}。
  • 四道守卫缺一不落盘：CAS（申请时的 config_hash ⇔ 当前文件指纹）· 只右移（delta ≥ 0）· 预算（d ≤ d_max）· 原子替换 + .bak + JSONL 审计；任一失败文件原样不动，但审计留痕。
  • plan_align 是纯函数：先出计划、策略链先检查，通过才落盘——所以 noop/retry/recheck 分支不会留下半成品。
  • truth 文件只装载设备、只参与事后对账：校准流程不读它，残差 max(q) − min(q) 是模拟端独有的硬回归指标。
  • 目标锚点取当前最靠右的那条线：只能右移 ⇒ 它既可达、又让总线位移最小， 于是逐线 δ_i = max(o) − o_i ≥ 0 天然满足单调守卫。
  • 两条编排主线，一套内核：pipeline.py 两阶段、不分组（一条 CLI 跑完全部线）； stages.py 四组六步、按物理依赖分组。两者共用 contracts / session / policies / center / writeback / graph / ledger / solver，区别只在"测哪些边、什么时候写"。
  • 测量日志就是批量流程的 WAL：每条边测完即往 pending 伴生文件 <stem>.measurements-audit.jsonl 追加一行（含 config_hash 与 stage_done 事件）。恢复判据由版本纪律直接给出：日志里 config_hash 与当前待测文件一致的合格观测，描述的正是眼前这个世界——重启后按边跳过不重测； hash 不一致的阶段已随写回生效，按事件整阶段跳过（headroom 授予台账一并重放， 末尾求解是确定性纯计算、重算即可）。重新生成 pending 视为开启新一轮，伴生日志自动作废。

接入 QXtrl（执行端 · 相对完善，积极开发中）

我们的契约字段QXtrl 侧对应物结论
config_hashRecipeResult.config_hash / CFG raw_hash语义天然一致，CAS 守卫可直接沿用其指纹，不必自造
quality / flagsQualityResult(status, score, metrics) · 拟合 _r2 · RecipeCell.warnings 映射即可；quality_min 阈值待其 score 口径确认后标定
sigma_ns / n_shotsRecipeCell.shots · step meta有 shots；标准误需由我们按 repeats 分组估计（SimExecutor 已是这个口径）
artifactsHDF5 归档 <archive_root>/<task_id>.h5 · VizRedis v2只放路径与哈希，符合既有约定（不内联数组）
skew_ns（主判据）未发现现成相对延时测量实验 真正的缺口：每条边的相对延时测量需在 QXtrl 侧新增原子实验（最接近的是 Ramsey 扫 delay）； 好消息是批量模式一轮只要 N−1 次实验，且彼此独立，天然适合排队提交
提交与并发client.submit() 阻塞 / aio 异步 · SubmissionSupervisor 队列 · hardware_hold 独占锁 · CLI 批处理先例 同进程用 DirectExecutor 最省；FileQueue 需薄封装申请⇄Atom+CFG 文件对；并发编排必须服从 hardware_hold（设备独占 → 编排"并行"只是排队）
延时写入归属其 analysis/act.py 也会原子回写自己的 CFG 风险项：两处都写延时会互踩。需明确唯一归属（当前设计：延时归审查中心， QXtrl 侧只被下发）

借鉴 automation（调度核心 · 筹备中，只取思路）

  • stage 五方法协议 prepare/analyze/decide/act/recover：正对应我们的 申请/分析/裁决/回写/补救；measure / finish 两阶段已各自成型，将来编排器按此协议注册即可。
  • attempt_id = submission_id 幂等补查：超时不重投而按 id 补取，比现在的 "retry 直接重发"更省设备时间——纳入 resubmit() 的演进方向。
  • Outcome 四态 PASS/FAIL/INCONCLUSIVE/INVALID：把"分析出错"与"校准不合格"分开， 比单一 retry 更准，可细化我们的 recheck / retry 分界。
  • path→stages 依赖失效映射：将来动态编排要回答"哪些线的位移使哪些测量边作废"， 这是最合适的表达雏形；作者刻意不自动回溯，与我们把全量编排推迟到末尾统一求解的判断一致。
  • fsync 的四段式 JSONL 条目（request/execution/analysis/decision）：我们的审计行可合并成 一条带全链证据的记录，回放更省事。
  • 不照搬：它的线性 stage 列表与"按位置回放"假设与并行编排冲突；我们的回放应按 request 内容匹配，而不是按 stage 顺序。
